# 山データの取得で分かったこと

OpenStreetMap（OSM）から山データを取得しようとしてつまずいたことと、開発中に分かったことの記録。
アプリは今、[yamamuki-data](https://github.com/shohei0205/yamamuki-data) が配る全国の山頂データだけを使い、Overpass API には問い合わせない。
Overpass を使っていたころのコード（`OverpassClient` など）は事前ダウンロードの機能と一緒に残してあり、`Features.AREA_DOWNLOAD`（iOS は `Features.areaDownload`）で無効にしている。

## Overpass API から直接取得していたころ

### 応答が来るまで長く待つ

- Overpass は集計が終わるまで何も返さない。0.5° 四方を数個まとめて問い合わせると 40 秒以上かかることがあった。
- Android の OkHttp は読み込みのタイムアウト（socketTimeout）の既定が 10 秒で、届く前に打ち切られていた。今は接続 15 秒・読み込み 75 秒・全体 90 秒にしている（iOS も 75 秒・90 秒）。
- 応答が届くまで受信量が増えないので、進み具合は「待っている秒数」で出すしかない（`DownloadProgress.statusText`）。

### サーバーの選び方と取り直し

- 代わりのサーバーとして使っていた overpass.kumi.systems（今は overpass.private.coffee）は、問い合わせに応答せず 75 秒待ってタイムアウトするだけだった。一覧から外したら、失敗が数秒で返るようになった（#34）。
- 本家 overpass-api.de の 504・429 は「同時に使える枠が空いていない」という意味。別のサーバーに回すより、少し待って同じサーバーに問い合わせ直すほうが通りやすい。
- 429 のあとは、OSM の利用方針に合わせて少なくとも 30 秒待った。504 などは 5・15・30 秒あけて取り直した。
- Overpass は共有の無料サービスで、問い合わせの回数と範囲を増やすと他の利用者の迷惑になる。一般公開すると利用者の数だけ問い合わせが増えるので、配布データに切り替えた（#35）。

### 通信量を減らす

- 応答を JSON（`out body`）から、使う列（ID・緯度経度・`name`・`name:ja`・`ele`）だけのタブ区切り CSV に変えると、1.0° 四方の実測で受信量が 21.3 KB から 12.9 KB（gzip 後）になり、約 4 割減った。
- CSV では値に改行を含む行などで列数が合わないことがある。見出し行で列を探し、列数が合わない行は読み飛ばした。

### 通信量の目安（Overpass から取っていたころの計測）

方位盤から 1 回取得したときに受信する量（gzip 圧縮後）。関東の低山が点在する地域で 2026 年 9 月に測ったもの。

| 取得半径 | 問い合わせる範囲 | 山の数 | 受信量 |
|---|---|---|---|
| 20km | 1.0° × 1.0° | 約 500 | 約 13 KB（実測） |
| 50km（起動時の標準） | 1.5° × 1.5° | 約 1,200 | 約 33 KB（推定） |
| 120km（最大に縮小したとき） | 2.5° × 3.0° | 約 2,400 | 約 65 KB（推定） |

- 推定値は、20km の実測値と、以前の JSON 形式で測った山の数・サイズの比から出したもの。送信量は、問い合わせ文の数百バイトと、接続ごとの TLS のやり取りで数 KB。
- 取得済みの地域では、設定の期間（既定 30 日）内は通信しなかった。初めての地域で起動したときに数十 KB、同じ地域で使い続けるなら期間が切れるまでほぼ 0 なので、日常的な利用なら月に数百 KB 程度と見ていた。
- 山の数は地域で大きく変わり、山の多い地域（日本アルプスなど）では上の表の 2〜3 倍になることがある。
- 都道府県単位の事前ダウンロードは、長野県で 20 区画・数百 KB と見積もっていた（推定）。
- これと比べると、今の配布データは全国分で約 0.45 MB（2026 年 10 月の開発版で 451,151 バイト）。県 1 つの事前ダウンロードと同じくらいの量で全国がそろい、最新版の確認は manifest（1 KB 未満、変わっていなければ HTTP 304）だけで済む。

### タグの読み方

- 名前は `name:ja`、`name` の順に使う。`name:ja` だけのノードもある。
- `ele`（標高）は数値だけとは限らない。`3776 m`、`424M`、`3,776`、`3776;3775`（先頭を使う）、`12345 ft`（m に直す）などがある。
- 名前のない山頂は数が多いので除く。way・relation の山は少ないので、ノード（`natural=peak` と `natural=volcano`）だけを取る。

### キャッシュの区切り方

- 0.5° 四方のタイル単位で取得とキャッシュをした。範囲を少し動かしても、問い合わせ直さずに済む。
- 山が 0 件のタイル（海など）も「取得済み」として時刻を記録する。記録しないと、毎回問い合わせ直したり「一部の山データがありません」と出たりする。
- 事前ダウンロードは 2×2 タイルずつ問い合わせた。北海道は 1 地域だと約 130 区画になるので、4 地域に分けた。都道府県の範囲は国土数値情報をもとにした簡略な境界から求めた矩形。

### クラウドの開発環境から試すとき

- Claude Code などのクラウド環境からは、Overpass・Nominatim・github.io への通信が 403 で拒まれることがある。動作の確認は手元の端末か GitHub Actions で行う。

## 配布データ（yamamuki-data）に切り替えて分かったこと

### データの作り方

- Overpass は使わず、Geofabrik の日本全国の PBF（約 2.5 GB）から `osmium tags-filter` で山頂だけを抜き出す。全国で約 14,000 件、gzip で約 0.45 MB（展開後 2.7 MB）なので、地域ごとに分けなくてよい。
- 形式は yamamuki-data の [peaks/README.md](https://github.com/shohei0205/yamamuki-data/blob/main/peaks/README.md) にある。アプリは manifest の `schemaVersion` が 4 のものだけを読み、知らない版なら「アプリを更新してください」と出す。

### 最新版の目印の置き場所

- はじめは固定の Release（`peaks-dev-latest`）の `manifest.json` を `gh release upload --clobber` で差し替えていた。この方法は古いファイルを消してから上げ直すので、その間にアプリが取りに来ると 404 になる。どれが公開済みかも Releases の一覧から分かりにくかった。
- 今は最新版の manifest を GitHub Pages に置き、データ本体は版ごとの Release に置く（manifest の `downloadUrl`）。差し替えの途中で欠けず、古い manifest が返っても対応する本体は取れる。
- GitHub の定期実行（`schedule`）はデフォルトブランチ（main）のワークフローでしか動かない。dev にだけ書いても毎月の自動生成は動かない。

### アプリでの取り込み

- manifest を取るときは前回の ETag を `If-None-Match` で送る。304 なら何も取らない。ETag が変わっても版（`version`）が同じなら、本体は取り直さない。
- 本体は展開する前に、manifest のサイズと SHA-256 に合うかを確かめる。合わなければキャッシュには手を付けない。
- 本体は gzip のファイルそのものとして配っている。Release のファイルは `Content-Encoding` なしで届くため、受け取ったバイト列をそのまま検証できる。サーバーが `Content-Encoding: gzip` を付けると、OkHttp も URLSession も HTTP の層で展開してしまい、サイズと SHA-256 が合わなくなる（取り込まずに失敗するので、壊れたデータは入らない）。
- iOS の Foundation には gzip を展開する関数が無い。ヘッダー（10 バイトと任意の項目）を飛ばし、中身の deflate を Compression で展開し、末尾の元の大きさ（ISIZE）で確かめている。
- 取り込むときは、日本の端の島まで入る範囲（北緯 20〜46°・東経 122〜154°）のタイルをすべて置き換える。これで海のタイルも取得済みになり、新しい版で消えた山や、以前 Overpass で取った山がキャッシュに残らない。iOS はタイルごとにファイルを作るので、約 3,400 個のファイルになる。

### データの中身の癖（#40 のレビューより）

OSM のデータそのものの癖なので、Overpass で取っていたころも同じものが表示されていた。今のところ配布データでは直していない。

- 名前が `305m`・`B1` のように標高や記号だけの山頂がある（約 140 件）。
- 同じ名前の山頂が 300 m 以内に重なっているものがある（約 40 組）。表示する山の選び方（#77）で、近くの重なりは標高の高いほうを残している。
- ふりがな（`name:ja-Hira`）に、`;` でつながった複数の読み、カタカナ、ローマ字、入力ミスが混じっている。
- 名前に `;` で複数の名前が入ったものや、`(Mt.Shiude)` のように英語の読みが括弧で付いたものがある。
- 海の中の火山（標高がマイナス）がある。標高のない山頂は約 7%。
